Looks fun, love adding new features. Here's my plan:

1. Add MCP-UI rendering inside Chat UI
first we want the chat UI to treat MCP-UI resources as VIP. The UI already handles generic MCP resources, so the logic becomes:

detect UIResources carrying the mcpui.dev/ui-* metadata
spin up an iframe with the MCP-UI client instead of treating the resource as static text/html
hook the iframe into our existing event bus so UI actions → Archestra actions
this means implementing the full postMessage contract (intent, notify, tool, prompt, link, data requests, render-data, and size updates). Chat UI basically becomes the “host” described in the MCP-UI spec.

2. Ensure the MCP Gateway passes UIResources cleanly
archestra’s MCP Gateway is the single ingress point, so we absolutely cannot mutate any UIResource payloads.
i'll validate that:

_meta, uiMetadata, blob encodings, and embedded resource fields survive the RPC boundary
UI actions coming from the iframe route back through the gateway the same way normal tool calls do
the gateway does not collapse/flatten/strip any fields that MCP-UI relies on
so we want here 3rd-party UI → MCP Gateway → MCP server → back → UI, with interactive UI intact.

3. Same thing for LLM Gateway
the LLM Gateway needs to behave identically from the UI’s point of view. That means:

if an LLM produces a UIResource, we normalize it so that Chat UI sees the same shape as if it came from a real MCP.
when the user interacts with an MCP-UI iframe, those actions must route back through the LLM Gateway without any branching logic.
If both gateways end up looking identical upstream, Chat UI stays simple and predictable.

4. Test with two real MCPs and add em to the catalog
i’ll use two very different MCPs so the whole protocol surface is exercised:

MCP A: simple HTML/uri-list style UI
MCP B: remote-dom / more interactive UI using the full MCP-UI event model (intents, data requests, etc....)
validate the whole loop: render → user clicks → action hits gateway → MCP responds → iframe updates.

5. Demo Time!
speaks for itself! showcase the awesome chat enhancement.

feel free to share any recs/changes. dope project and would love to be assigned to this. thanks! @Matvey-Kuk

Thank you @iskhakov for the detailed questions! Here are my answers:

MCP Apps Compatibility
Yes, this will be fully compatible with MCP Apps. Both MCP UI and MCP Apps use the same postMessage protocol and the application/remote-dom+json format. My MCPUIRenderer component will detect both the legacy mcpui.dev/ui-* metadata and the new MCP Apps format, so it'll work seamlessly with both as the ecosystem migrates.
Test MCPs
I'll use two MCPs:
Filesystem MCP - The official one from modelcontextprotocol/servers. It's simple, uses text/html, and perfect for testing basic iframe rendering and tool calls like read_file and list_directory.
Weather Dashboard MCP - I'll build a custom one using application/remote-dom+json with interactive charts. This tests the full MCP Apps protocol including intents, data requests, and complex user interactions.
Both will be added to the catalog with documentation.
MCP Gateway Integration
The key challenge is preserving UIResources through the gateway without breaking the metadata. Here's my approach:
UIResource Preservation - I'll modify the resources/read endpoint to pass through all fields including blob, _meta, and custom MCP UI fields unchanged.
New UI Action Endpoint - Adding POST /mcp-gateway/:serverId/ui/action to route iframe interactions back to the MCP server. When users click buttons or interact with the UI, those actions get forwarded as tool calls, data requests, or prompts.
Capabilities Discovery - New GET endpoint that checks which servers support UI by looking at their resource mimeTypes.
For third-party apps, the flow is: discover capabilities → fetch UIResource → render iframe → handle postMessage events → route actions through gateway → update UI with responses.
I'll build a test HTML page that connects to the gateway and validates the full loop works.
LLM Gateway Integration
This is trickier since LLMs don't return UIResources natively. My approach:
Intent Detection - Parse LLM responses for UI intent (phrases like "I'll show you an interactive chart" or special markers).
UIResource Generation - When detected, generate proper HTML with MCP protocol handlers embedded. The HTML includes postMessage setup and action routing back to the gateway.
Action Handling - New POST /llm-gateway/ui/action endpoint that takes UI actions, routes them back to the LLM with context, and returns updated UI or text responses.
For third-party apps: send message → LLM returns UIResource → render iframe → user interacts → route action through gateway → LLM processes → update UI.
I'll test with scenarios like chart generation, form interactions, and multi-step workflows to ensure the context is maintained throughout.
The main complexity in both gateways is ensuring UIResources survive the proxy layer without losing metadata, and properly routing UI actions back through the same gateway so third-party apps don't need to know about the underlying MCP servers or LLMs.
